一、整体架构设计
================================================================================

MemoryDatabase 是整个系统的唯一数据真相源，实现了多部分数据结构：

    第0部分: 车型及性能指标维度基本信息
        └─ 硬盘记忆（***.xlsx）文件中 VTS sheet 所包含的"车型"和"类别"_"一级"的条目
        └─ 用于计算流和响应界面动态更新的参考信息

    第1部分: 完整版 memory_dbs
        └─ 工程计算专用，按Sheet/车型/分类/数据类型分层

    第2部分: inter_memory_dbs 中间变量命名空间            
        └─ 计算节点间数据交互中转站，随动态更新的计算流更新
                                                                                                                       
    第3部分: 简化版 memory_dbs_simplified （LLM 内存数据库中对应推理上下文的数据源；简化汇总 第1部分: 完整版 memory_dbs；第2部分: inter_memory_dbs 中间变量命名空间）                       
        └─ 自然语言LLM对话用，树状嵌套列表 
            ├─ 内存记忆_base    (基准值)
            ├─ 内存记忆_上一轮  (快照参照)
            └─ 内存记忆_当前    (计算实时值)
    
    第4部分: 历史快照 history_snapshots（LLM 推理上下文数据源）
        └─ 差异快照，版本追踪与回滚

    第5部分: 表格或者曲线类参数（计算工况或者零部件级参数）
        └─ 驾驶循环 drive_cycles

设计原则:
  ✅ Core 层绝对干净，不碰 UI、不碰 asyncio、不碰 threading
  ✅ 所有模块共享同一个 MemoryDatabase 单例
  ✅ 计算节点/LLM/UI 都从此处取数，唯一真相源
  ✅ INTER 层实现：一份数据 = 计算交互 + LLM推理 双用途
  ✅ 简化版自动汇总完整版 + INTER，LLM 统一入口

================================================================================
四、第2部分: inter_memory_dbs 中间变量命名空间
================================================================================

------------------------------
4.1 设计定位：一份数据，两种用途
------------------------------

        inter_memory_dbs
              │
      ┌──────┴──────┐
      │             │
  计算节点数据流    LLM推理输入
（下游节点读值） （取出关键结果）

设计目标:
  ✅ 消除节点间硬编码依赖，统一数据交互总线
  ✅ 计算结果自动可用于LLM推理，不需要二次转换
  ✅ 按工作流实例完全隔离，多车型并行无干扰

------------------------------
4.2 完整数据结构
------------------------------

三层结构，确保多实例完全隔离：

    {workflow_instance_id}.{var_name} = {
        # ---------- 给计算算法用的 ----------
        "value": Any,                # numpy数组、float、int等原始值
        "source_node": str,          # 来源节点类型ID

        # ---------- 给 LLM 和 UI 用的 ----------
        "display_name": str,         # 人类可读名称
        "unit": str,                 # 单位
        "description": str,          # 详细说明
        "llm_relevant": bool,        # ✅ 关键：是否需要传给LLM

        # ---------- 系统元数据 ----------
        "timestamp": datetime,       # 写入时间
        "node_id": str,              # 来源节点ID
    }

------------------------------
4.3 标准对外API
------------------------------

给计算节点用的接口:

  inter_write(workflow_id, var_name, value, ...)
    - 节点写入输出中间变量，自动带上完整元数据
    - 调用者：节点基类.run()，子类代码不用管

  inter_read(workflow_id, var_name) -> value
    - 下游节点只读原始value，简洁高效
    - 调用者：CalculationNode.get_input()

  inter_clear(workflow_id)
    - 计算前清空该工作流的所有中间变量
    - 调用者：Workflow.run_all() 第一行

给 LLM 推理用的接口:

  inter_get_llm_context(workflow_id) -> List[Dict]
    - ✅ 自动过滤 llm_relevant=True 的变量
    - 自动格式化，直接可以拼入 prompt
    - 返回示例：
      [
        {"名称": "车端能耗", "数值": "15.2", "单位": "kWh/100km"},
        {"名称": "续驶里程", "数值": "405", "单位": "km"},
      ]

  inter_read_full(workflow_id, var_name) -> full_meta
    - 调试用，读取变量的完整元数据

------------------------------
4.4 命名约定 & 隔离规则
------------------------------

var_name 命名规范:
    {节点类型}_{变量名}

    示例:
        DriveCycleAnalyzer_Lth
        Resistance_F_all
        VehicleEnergy_E_DC

workflow_instance_id 规范:
    {领域}_{车型}_{序号}

    示例:
        ECO_增程_001
        ECO_纯电_001
        POWER_增程_001

✅ 隔离保证：不同车型、不同计算领域的中间变量绝对不会互相干扰

------------------------------
4.5 节点声明方式（侵入性极小！）
------------------------------

在节点类的 register_output 加一个参数即可：

    # 原来的写法
    self.register_output("E_DC", "车端能耗", "kWh/100km")

    # ✅ 改造后（就加一个参数！）
    self.register_output("E_DC", "车端能耗", "kWh/100km",
                         llm_relevant=True,
                         description="整车高压母线端百公里能耗")

✅ 向后兼容：不加 llm_relevant 参数也能正常运行，只是不进LLM上下文

------------------------------
4.6 自动写入机制
------------------------------

基类 CalculationNode.run() 自动完成：

    1. 执行子类 calculate() 得到输出字典
    2. 遍历所有 register_output 声明的变量
    3. 自动带上 display_name、unit、llm_relevant 标记
    4. 调用 inter_write() 写入数据库

✅ 子类代码一行都不用改！

五、第3部分: 简化版 memory_dbs_simplified
================================================================================

------------------------------
5.1 设计目标
------------------------------
  - 【重要改进】自动汇总：第1部分完整版 + 第2部分INTER
  - 与UI展示层 build_memory_db_tiles() 结构完全对齐
  - 移除冗余字段（代号、相关性标签），只保留核心三字段
  - 供"自然语言内存记忆"页面树状展示使用
  - LLM 只需要读这一层，不用管底层结构

------------------------------
5.2 核心转换算法 _simplify_memory_db()
------------------------------

处理流程:

    第1部分: 完整版 memory_dbs
         ↓
    遍历每个 sheet_name
         ↓
    遍历每个分类 key
         ↓
    遍历每个参数 item
         ↓
    提取 {名称, 单位, 数值} 三字段
         ↓
    第2部分: inter_memory_dbs
         ↓
    遍历每个 workflow_instance_id
         ↓
    过滤 llm_relevant=True 的变量
         ↓
    统一格式：{名称, 单位, 数值}
         ↓
    合并写入简化版的 "中间计算结果" 分类

简化后结构:
    "内存记忆_base": {
        "VTS": {                                    ← Sheet级
            "增程_动力性_加速性能_目标值": [         ← 分类级
                {"名称": "0-100km/h", "单位": "s", "数值": 7.5},  ← 参数级
                ...
            ],
        },
        "SSTS": {...},
        "产品定义": {...},
        "INTER": {                                  ← ✅ 新增：中间计算结果
            "车端能耗": {"数值": 15.2, "单位": "kWh/100km"},
            "续驶里程": {"数值": 405, "单位": "km"},
            ...
        }
    },
    "内存记忆_上一轮": {...},  ← 用于快照差异比较
    "内存记忆_当前": {...}     ← 计算后实时更新

------------------------------
5.3 版本更新机制
------------------------------

                              【全局自动同步】
        完整版/INTER 修改 → 自动同步 → 内存记忆_当前
                   用户调参 ✓  计算节点执行 ✓  LLM修改 ✓

三版本职责分工:

  ┌─ 内存记忆_base
  │   └─ Excel加载完成时生成一次，【永远不变】，作为手动快照比较基准
  │
  ┌─ 内存记忆_当前
  │   └─ 【实时自动同步】完整版 + INTER 的任何修改
  │   └─ 用户/计算节点/LLM 都能看到最新值
  │
  └─ 内存记忆_上一轮
      └─ 【只有LLM能修改】LLM function calling begin 时才备份一次

方法调用时机:

  ┌─ initialize_simplified_base()
  │   └─ 首次加载Excel时调用，三版本初始化为相同值

  ┌─ _auto_sync_simplified()
  │   └─ 完整版/INTER 修改时【自动调用】，用户/代码都不用管
  │
  └─ llm_snapshot_begin() + llm_snapshot_commit()
      └─ 【LLM专属】事务式快照，begin打基准，commit打快照

------------------------------
5.4 两套快照体系的区别
------------------------------

| 快照类型 | 触发者 | 比较基准 | 版本推进 | 快照来源标记 |
|---------|-------|---------|---------|-----------|
| ✅ LLM事务快照 | LLM | 内存记忆_上一轮 | commit后自动推进 | LLM |
|   手动快照 | 用户按钮 | 内存记忆_base | 不推进版本 | 手动 |

------------------------------
5.5 LLM快照事务模型（begin + commit）
------------------------------

完整时序（LLM function calling 必须严格遵守）:

          LLM 准备调用 Function
                     ↓
  1. ✅ llm_snapshot_begin()
       └─ 内存记忆_上一轮 = 内存记忆_当前【打基准】
       └─ 【关键分界点】这之后的修改才会被记录
                     ↓
  2. 执行 Function Calling
       └─ 修改完整版 / INTER 参数
       └─ 自动同步到 内存记忆_当前
                     ↓
  3. ✅ llm_snapshot_commit("修改了XXX参数")
       ├─ 差异比较：内存记忆_上一轮 ↔ 内存记忆_当前
       ├─ 有差异才打快照，快照来源标记为"LLM"
       └─ 【注意】基准不自动推进，下次begin再打新基准

完整代码示例:
```python
# LLM 层调用代码
memory_db.llm_snapshot_begin()    # 第一步：打基准
try:
    memory_db.set("SSTS.增程.Mass", 1850)  # 中间修改自动同步
finally:
    memory_db.llm_snapshot_commit("LLM调整增程版整备质量")
```

✅ 核心优势:
  - 再也不会"忘记同步简化版"了，修改自动同步
  - 用户调参、跑计算都不会污染快照系统
  - 只有LLM的操作才会被记录到历史快照
  - 事务式begin/commit，支持try/finally异常安全


================================================================================
六、第4部分: 差异快照系统实现逻辑
================================================================================

------------------------------
6.1 设计理念
------------------------------
  ✅ 只存差异，不存全量 → 占用空间极小
  ✅ 无差异不创建快照 → 避免空快照
  ✅ 自动轮转 → 超过100个自动删除最早的
  ✅ 自动生成描述 → 变更内容一目了然

------------------------------
6.2 核心算法 _compare_simplified_dbs()
------------------------------

比较维度: 内存记忆_当前 VS 内存记忆_上一轮

比较流程:

    1. 遍历每个 sheet_name
    2. 遍历每个分类 key
    3. 按索引逐个比对参数列表
    4. 仅检测 "数值" 字段变化
    5. 记录差异: {名称, 单位, 数值, 原数值}

差异输出结构:
    {
        "VTS": {
            "增程_动力性_加速性能_目标值": [
                {
                    "名称": "0-100km/h加速时间",
                    "单位": "s",
                    "数值": 7.5,   ← 新值
                    "原数值": 7.8  ← 原值
                },
                ...
            ]
        }
    }

UI自动高亮:
  - 检测到 "原数值" 字段存在时
  - 显示格式: 名称 : 原数值 单位 → 新数值 单位
  - 效果: 0-100km/h加速时间 : 7.8 s → 7.5 s

------------------------------
6.3 create_snapshot() 完整执行流程
------------------------------

                      ┌─────────────────────────┐
                      │   调用 create_snapshot() │
                      └────────────┬────────────┘
                                   │
                                   ▼
    ┌─────────────────────────────────────────────────────┐
    │ 1. 差异比较 _compare_simplified_dbs()               │
    │    当前值 VS 上一轮值                                │
    └───────────────────────┬─────────────────────────────┘
                            │
                ┌───────────┴───────────┐
                │ 有差异?               │ 无差异
                ▼                       ▼
    ┌──────────────────────┐    ┌──────────────────┐
    │ 2. 快照计数器+1      │    │ 返回 None        │
    │    快照N → 快照N+1   │    │ 不创建快照       │
    └───────────┬──────────┘    └──────────────────┘
                │
                ▼
    ┌─────────────────────────────────────────────────────┐
    │ 3. 自动生成快照描述                                  │
    │    - 取前5项变更名称拼接                            │
    │    - 超过5项: "参数A、参数B 等N项变更"              │
    └───────────────────────┬─────────────────────────────┘
                            │
                            ▼
    ┌─────────────────────────────────────────────────────┐
    │ 4. 存储差异快照                                      │
    │    {生成时间, 快照描述, 快照内容=diff}               │
    └───────────────────────┬─────────────────────────────┘
                            │
                            ▼
    ┌─────────────────────────────────────────────────────┐
    │ 5. 快照轮转                                          │
    │    数量 > MAX_SNAPSHOTS(100) → 删除最旧快照         │
    └───────────────────────┬─────────────────────────────┘
                            │
                            ▼
    ┌─────────────────────────────────────────────────────┐
    │ 6. 版本推进                                          │
    │    内存记忆_上一轮 = 内存记忆_当前                   │
    └─────────────────────────────────────────────────────┘

八、核心辅助方法说明
================================================================================

------------------------------
8.1 _extract_value(row, col)
------------------------------
功能: 从Excel行中安全提取值，处理多级标题
实现:
  - 支持 tuple 类型的多级列名
  - 自动去除换行符、回车符
  - strip() 移除首尾空格

------------------------------
8.2 _convert_value_type(value)
------------------------------
功能: 智能数值类型转换
优先级:
  1. 尝试 int() 转换
  2. 失败则尝试 float() 转换
  3. 都失败保留原始 str()
用途: 确保"数值"字段可以直接参与数值计算

------------------------------
8.3 列名映射算法
------------------------------
约50行特殊处理逻辑：

  1. 车型代号匹配时跳过数据类型列干扰
     - 避免把 "增程目标值代号" 错误匹配给 "增程代号"

  2. VTS sheet代号精确匹配
     - 只匹配第二行为"代号"的列

  3. 三级回退机制
     {车型}{数据类型}代号 → {车型}代号 → {车型}目标值代号

  4. 标题结构兼容
     - VTS: 四级标题兼容
     - 产品定义/SSTS: 三级标题兼容
     - 通用: 二级标题兼容

简化版更新:
  update_simplified_current()
    - 计算节点/LLM 修改参数后调用，刷新简化版当前值

LLM 专用接口:
  update_simplified_current() + create_snapshot(description)
    - 严格时序: 先同步简化版，再打快照
    - 支持多次修改后批量打快照

INTER 中间变量专用接口:
  inter_write(workflow_id, var_name, value, ...)
    - 写入中间变量，带完整元数据

  inter_read(workflow_id, var_name) -> value
    - 读取中间变量原始值（供计算使用）

  inter_clear(workflow_id)
    - 清空指定工作流的所有中间变量

  inter_get_llm_context(workflow_id) -> List[Dict]
    - 提取LLM推理上下文（所有标记的变量）
